# 作業ログ

「いつ・何を・なぜそう決めたか」の記録。**1日1ファイル**、`docs/log/YYYY-MM-DD.md`。

## なぜ残すか

1. **10/5 MTG の進捗報告の一次資料**。当日に思い出しながら書くと精度が落ちる。
2. **判断の根拠の保全**。閾値・プロンプト・分割ルールは後から必ず「なぜこの値か」を問われる。
3. **Phase 2 への引き継ぎ**。MVP を誰が引き継いでも経緯を追える状態にする。

## 書式

```markdown
# 作業ログ YYYY-MM-DD

## HH:MM 見出し（何をしたか一言で）

- **やったこと**: 実際に手を動かした内容。ファイル名・コマンドを含める
- **決めたこと**: 設計判断とその理由。要件定義の該当節があれば §番号を書く
- **数値**: 評価セットの実測値など（未実行なら「未実行」と書く。推測値を書かない）
- **残課題 / 次の一手**: 次に着手する人（未来の自分を含む）が迷わない粒度で
```

不要な項目は省いてよい。`やったこと` だけの短いエントリでも、**空欄より必ず良い**。

## いつ書くか

以下のたびに追記する。まとめて書かない。

- 作業のまとまりが終わったとき（機能1つ、パイプライン1段、画面1枚）
- **設計判断をしたとき**（採用/不採用の両方とその理由）
- **詰まったとき・想定外が起きたとき**（解決前でも書く。ハマった事実自体が情報）
- 評価セットを回したとき（必ず実測値を残す）
- 作業を中断するとき

## 運用ルール

- **ログは書き換えない。追記のみ。** 判断が覆ったら、取り消し線ではなく新しいエントリに「◯◯を撤回」と書く。経緯が消えると価値がなくなる。
- 実規程の条文本文・個人情報・パスワードをログに貼らない（このファイルは git 管理下にある）。
- 時刻は日本時間。
