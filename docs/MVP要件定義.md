# 社内規程AI確認システム — MVP要件定義

- 対象: 株式会社大和田測量設計「ミニDX化支援業務」
- 作成: 会津大学チーム / 2026年9月23日
- 次回共有: 2026年10月5日（月）MTG
- 典拠（受領資料・変更不可）: [開発仕様](社内規程AI確認システムの開発仕様.md) / [キックオフ議事録](2026-09-03_キックオフMTG議事録.md)

---

## 0. このMVPで証明したいこと

本件の価値は「AIが社内規程に答えられること」ではない。同種のツールは既製品にもある。
価値は **「根拠のない回答を、仕組みとして出させないこと」** にある。

したがってMVPの成否は次の一点で判定する。

> **規程に書かれていない質問に対し、一度も「それらしい回答」を出さないこと。**

「答えられる質問に答える」のは副次的な達成目標であり、「答えられない質問に答えてしまう」のは
このプロジェクトにおける**致命的欠陥**として扱う。10/5のデモはこの非対称性を中心に構成する。

## 1. スコープ確定

### 1.1 作るもの（MVP）

| # | 構成要素 | 内容 |
|---|---------|------|
| 1 | 規程取込パイプライン | PDF → Markdown → 条文単位に分割してDB登録（CLI） |
| 2 | ハイブリッド検索 | BM25（語彙一致）＋ bge-m3（意味一致）で該当条文を検索 |
| 3 | **二段棄却ゲート** | 検索スコア閾値 ＋ 引用実在性検証。本システムの中核 |
| 4 | 回答生成 | 取得条文のみを根拠にローカルLLMが日本語で回答 |
| 5 | Streamlit アプリ | 社員タブ（質問→回答＋根拠条文）／管理者タブ（未整備一覧） |
| 6 | 質問ログDB | 全質問と判定結果を記録、未整備質問を頻度順に集計 |
| 7 | 公開構成 | Cloudflare Tunnel でローカル実行のまま一時公開。アプリ内パスワードゲート付き |

### 1.2 作らないもの（Phase 2 以降）

明示的にMVP範囲外とし、10/5 MTGでもそう説明する。

- kintone / サイボウズ Office への統合（← 将来の理想構成。MVPでは疎結合な単体アプリに留める）
- ユーザー認証・権限管理・複数同時利用
- 規程改定の差分管理・版管理UI（DBスキーマ上は版を持つが、運用UIは作らない）
- OCR処理（テキスト層のないPDFは対象外。後述 3.2）
- Windows向けインストーラ / ポータブルSSD納品パッケージ化（最終納品形態。後述 7.6）
- 回答へのフィードバック（Good/Bad）収集

## 2. アーキテクチャ決定

### 2.1 全体構成

```
[規程PDF] ──ingest──> [Markdown] ──分割──> [SQLite: articles(条文+ベクトル)]
                                                      │
社員の質問 ──> ①ハイブリッド検索 ──> ②スコアゲート ──┤
                                          │ 不合格    │ 合格
                                          ↓           ↓
                                    【未整備判定】  ③LLM回答生成（取得条文のみ）
                                          ↑           ↓
                                          │      ④引用実在性検証
                                          └───不合格──┤ 合格
                                                      ↓
                                              回答 ＋ 根拠条文表示
                                          （全経路を query_log に記録）
```

### 2.2 技術選定と根拠

| 領域 | 採用 | 根拠 |
|------|------|------|
| 実行形態 | **推論・データは完全ローカル** | 議事録合意事項。LLMへの問い合わせは localhost で完結し、外部AI APIは使わない。ポータブルSSD納品構成をそのまま検証できる（ただし公開時の通信経路のみ Cloudflare を経由する。7.5） |
| LLM | Ollama `qwen2.5:7b` | 導入済み。日本語品質と7Bクラスの速度のバランス。指示追従性が高く「答えない」制御が効く |
| 埋め込み | Ollama `bge-m3` | 導入済み。多言語モデルで日本語の意味検索に強い。1024次元 |
| ベクトル検索 | **numpy 全件総当たり** | 15規程＝数百〜2,000条文規模。専用ベクトルDBは不要な複雑さ。数ms で完了する |
| 語彙検索 | BM25（`rank_bm25`）＋ `fugashi`/`unidic-lite` | 「日当」「通勤手当」等、規程特有語の完全一致を拾う。ベクトル単独では取りこぼす |
| 永続化 | SQLite 単一ファイル | 納品時にファイル1つをコピーするだけ。サーバ不要 |
| UI | Streamlit | 短期で社員用・管理者用の両画面を出せる。10/5 の見せ場を優先 |
| Python | 3.12（uv で固定） | ライブラリ互換性。環境の 3.14 は使わない |
| 公開手段 | Cloudflare Tunnel（クイックトンネル） | サーバ費用ゼロ・ドメイン不要・ポート開放不要。**推論とデータは開発機内に留まる**（後述 7） |

**ベクトルDBを使わない判断について**: 規程数が2桁、条文数が3桁である以上、
インデックス構造の導入は性能ではなく運用負債にしかならない。numpy 配列で全件保持し、
起動時にロードする。将来 1万条文を超えた時点で再検討する。

## 3. 機能要件

### 3.1 規程の登録（F-01）

- CLI コマンド `ingest` で `data/raw/*.pdf` を一括処理する。
- PDF → Markdown 変換は `pymupdf` のテキスト抽出を使う。
- 変換結果の Markdown は `data/markdown/` に**中間成果物として残す**。
  抽出崩れを人が目視修正し、再取込できるようにする（議事録の「Markdown形式への変換を推奨」に対応）。
- 規程ごとにメタ情報（規程名・施行日・版）を `data/regulations.yaml` で管理する。

### 3.2 条文単位の分割（F-02）

- `第○条` を境界として分割する。項（`２`）・号（`（1）`）は親条文に含める。
- 条見出し `（出張日当）` が存在する場合はメタデータとして保持し、検索対象に含める。
- 1条が長大な場合（目安 1,200文字超）は項単位に再分割するが、条番号メタデータは引き継ぐ。
- **OCRは実装しない。** テキスト層のないPDFは取込時にエラーとして一覧報告し、
  「Markdown手動変換が必要な規程」として客先に返す。MVPで自動OCRに踏み込むと、
  抽出精度の不確実性が回答品質の不確実性に直結し、本件の中核要件を検証できなくなる。

### 3.3 検索（F-03）

- 質問文に対し BM25 と bge-m3 コサイン類似度をそれぞれ算出。
- Reciprocal Rank Fusion で統合し、上位 k=5 件を候補とする。
- 検索対象テキストは「規程名 ＋ 条見出し ＋ 条文本文」を連結したもの。

### 3.4 二段棄却ゲート（F-04）★最重要

**ゲート1: 関連性スコア閾値**

融合スコア最上位が閾値を下回る場合、**LLMを一切呼ばずに**未整備判定を返す。
呼ばなければ幻覚は原理的に発生しない。閾値は評価セット（5.2）でキャリブレーションし、
`config.yaml` で調整可能にする。

**ゲート2: 引用実在性検証**

LLM には以下の構造化出力を強制する。

```json
{
  "sufficient": true,
  "answer": "出張日当は日帰りの場合 2,000 円です。",
  "citations": [{"regulation": "旅費規程", "article": "第8条"}]
}
```

生成後、`citations` の各要素が**実際に検索で渡した条文集合の中に存在するか**を
プログラムで照合する。存在しない規程名・条番号が1件でも含まれていれば、
回答文の内容にかかわらず**全体を棄却**し未整備扱いとする。

LLMの自己申告（`sufficient`）を信用しない点がこの設計の要点である。
自己申告はゲート2への入口に過ぎず、最終判定は機械的照合が行う。

### 3.5 回答生成（F-05）

- システムプロンプトに以下を明記する。
  - 提供された条文以外の知識を使用してはならない
  - 一般的な労働基準法・世間の慣行に基づく補足を行ってはならない
  - 条文から判断できない場合は `sufficient: false` を返すこと
- `temperature = 0`。再現性を確保し、デモでの挙動を安定させる。
- コンテキストには検索で得た k=5 件の条文全文のみを入れる。

### 3.6 社員向け画面（F-06）

- 質問入力欄と回答表示。
- **該当ありの場合**: 回答文 ＋ 根拠条文カード（規程名／第○条／条見出し／条文原文）。
  条文原文は折りたたみで全文を確認できるようにする。
- **未整備の場合**: 回答を一切出さず、次の固定文言を表示する。

  > 社内規程を確認しましたが、ご質問に該当する条文は見つかりませんでした。
  > この内容は未整備の可能性があります。総務ご担当者へ直接ご確認ください。
  > （このご質問は未整備候補として記録しました）

  参考条文の提示も行わない。「近いものを出す」挙動は誤読を誘発するため設けない。

### 3.7 管理者向け画面（F-07）

- **未整備質問一覧**: 質問文・発生回数・直近日時。回数の多い順に表示。
  これが客先の言う「社内規程の網羅性・整備状況の不備の把握」に直接対応する成果物。
- **回答済み質問一覧**: 質問・回答・引用条文。総務担当者が回答の妥当性を検証できる。
- **取込状況**: 登録済み規程一覧（規程名・条文数・施行日・取込日時）。
- CSV エクスポート。

### 3.8 ログ（F-08）

全質問を SQLite に記録する。記録項目:
質問文 / 判定（answered・rejected_low_score・rejected_bad_citation）/ 最上位スコア /
検索ヒット条文ID / 回答文 / 応答時間。

判定内訳を分けて記録することで、閾値調整の根拠データになる。

## 5. 受入基準

MVPの完成は、実装完了ではなく以下の数値で判定する。

### 5.1 評価セット

| 種別 | 件数 | 内容 |
|------|------|------|
| 回答可能質問 | 15問 | 登録済み規程に明確な根拠条文が存在する質問。仕様書の質問例4問を含む |
| **回答不能質問** | 15問 | 規程に記載のない事項。「在宅勤務のルールは？」「副業は可能か」「育児短時間勤務の適用範囲は」等 |

回答不能質問セットは、社内規程に存在しないが**社員が実際に聞きそうな**内容で構成する。
無関係な質問（「今日の天気は」）では棄却ゲートの検証にならない。

### 5.2 合格ライン

| 指標 | 基準 | 位置づけ |
|------|------|---------|
| **誤回答率（回答不能質問に回答してしまう率）** | **0%** | **絶対条件。1件でも出れば不合格** |
| 検索再現率（正解条文が上位5件に含まれる率） | ≥ 80% | 品質目標 |
| 回答正確性（根拠条文の引用が正しい率） | ≥ 90% | 品質目標 |
| 応答時間 | ≤ 20秒／問 | ローカル7B推論の実測目標 |
| 過剰棄却率（回答可能質問を誤って棄却する率） | ≤ 20% | 許容。棄却側に倒すのが本件の設計思想 |

**過剰棄却を許容する理由**: 答えられるのに答えないことの損失は「総務に聞き直す」で済むが、
誤った回答は規程違反や手当の誤請求に直結する。閾値調整に迷った場合は常に棄却側に倒す。
この非対称性を客先にも明示的に合意いただく。

## 6. 10/5 MTG デモシナリオ

1. **登録状況の提示** — 管理者画面で取込済み規程一覧を表示
2. **回答できる質問** — 「出張の日当はいくらですか」→ 回答＋旅費規程 第○条を原文で提示
3. **表現を変えた質問** — 「泊まりの出張だといくらもらえる？」→ 同じ条文に到達（意味検索の価値）
4. **回答できない質問** — 「在宅勤務のルールはありますか」→ **未整備判定。回答しない**
5. **未整備の蓄積** — 管理者画面に 4 の質問が未整備候補として記録されていることを提示
6. **推論がローカル完結であることの実演** — **開発機の実機画面で**ネットワークを切断し、
   2〜4 を再実行して同じ回答が返ることを示す

**6 は必ず実機のローカル画面で行う。** 公開URL（Cloudflare Tunnel）経由では回線切断時に
画面ごと落ちるため実演にならない。トンネルはあくまで遠隔参加者への共有手段であり、
「LLM推論が外部APIに依存していないこと」の証明は実機でしかできない。この使い分けを
説明せずにトンネル経由でデモすると、かえって「クラウドで動いている」と誤解される。

## 7. 公開構成（Cloudflare Tunnel）

### 7.1 方針

開発機で動く Streamlit を Cloudflare Tunnel のクイックトンネルで一時公開する。
サーバ費用ゼロ、ドメイン取得不要、ポート開放不要、コマンド1行。

```
[利用者ブラウザ] ──HTTPS──> [Cloudflare エッジ]
                                    ↑ アウトバウンド接続
                            [開発機: cloudflared]
                                    ↓
                        [Streamlit :8501] ──> [Ollama :11434 / SQLite]
```

cloudflared がエッジへアウトバウンド接続を張る方式のため、グローバルIPも
ルータのポート開放も不要。**LLM推論とデータは開発機から一歩も出ない**
（Ollama への問い合わせは localhost:11434 で完結する）。

### 7.2 起動手順

```bash
brew install cloudflared                                    # 未インストール
uv run streamlit run app.py --server.port 8501 --server.headless true
cloudflared tunnel --url http://localhost:8501
# → https://<random-words>.trycloudflare.com が払い出される
```

### 7.3 認証（アプリ内パスワードゲート）

クイックトンネルには認証レイヤーが存在しない。**Streamlit 側で必ず実装する。**

- 未認証時は `st.stop()` で**UIもデータも一切描画しない**。タブやサイドバーの
  存在すら見せない（何のシステムかを推測させない）
- パスワードは `.streamlit/secrets.toml` に**ハッシュ値で**保持。平文禁止、`.gitignore` 必須
- **社員用と管理者用でパスワードを分ける。** 管理者タブの質問ログには
  全社員の質問履歴（誰が何を気にしているか）が入るため、同一パスワードで見せてはならない
- 認証失敗時は数秒スリープを挟み、総当たりの試行速度を鈍化させる
- `robots.txt` で `Disallow: /` を返し、検索エンジンへの露出を防ぐ

### 7.4 運用ルール（実データを載せるための必須前提）

実際の社内規程を載せる以上、以下を**運用ルールとして固定する**。

1. **トンネルを常時起動しない。** デモ・試用の時間帯だけ起動し、終了後は必ず落とす。
   クイックトンネルのURLは起動のたびに変わるため、これ自体が実効的な防御として働く
2. **URLは都度クローズドな手段で共有する。** メールやチャットに残さない
3. 開発機がスリープするとトンネルは切れる。デモ中は `caffeinate -s` で抑止する
4. 試用が数日以上に及ぶ場合はこの構成を継続せず、Named Tunnel + Cloudflare Access
   （メールOTP・メールドメイン制限・50ユーザーまで無料）へ移行する。
   ドメイン取得（年1,500円程度）が必要になるが、認証と監査証跡が手に入る

### 7.5 残存リスク（設計では消せないもの）

以下は技術で解消できないため、**客先の承諾事項**として扱う（§9-5）。

- **TLS は Cloudflare エッジで終端される。** 質問文と、回答に含まれる条文本文は
  Cloudflare のネットワークを経由する。LLM推論そのものは完全ローカルだが、
  「社内規程のテキストが外部事業者のネットワークを通る」点は、議事録の
  「外部データ連携を伴うサービスの利用は回避したい」という意向と厳密には一致しない。
  **事前承諾なしに実規程を載せてはならない**
- **共有パスワード方式では利用者を識別できない。** 誰がいつアクセスしたかの
  監査証跡が残らない。これが要件化した時点で Access への移行が必須になる
- クイックトンネルは SLA・稼働保証がなく、同時 200 リクエストの上限がある。
  Streamlit は利用者1人につき WebSocket を1本占有するため、実質的な同時利用者上限も 200
- Cloudflare はクイックトンネル上で新機能の試験を行うと明言しており、本番用途を想定していない

### 7.6 最終納品形態との関係

Tunnel は**開発期間中の共有とデモのための手段**であり、納品形態ではない。
客先への最終納品は議事録どおり、ファイルサーバまたはポータブルSSD経由での
社内設置を想定する（Phase 2）。**この区別を 10/5 MTG で明示する。**
説明を省くと「クラウドサービスを導入する話」と受け取られ、
ローカル構築という前提そのものが崩れる。

## 9. 客先への確認事項（10/5 MTG で提起）

1. **規程PDFの全件提供**（約15種類）。現状は一部のみ受領。
   テキスト層のないPDFの有無を早期に確認したい。
2. **過剰棄却の許容合意**（5.2）。「答えられるはずの質問に答えない」ケースが
   一定割合発生することを設計思想として合意いただく。
3. **未整備質問の運用主体**。蓄積した未整備リストを誰がどの頻度でレビューし、
   規程改定につなげるか。ここが決まらないと「可視化」が成果物で終わる。
4. **Phase 2 の方向性**。kintone 連携か、ファイルサーバ設置型の社内Webアプリか。
   議事録ではサイボウズ統合が理想とされたが、クラウド版 kintone への
   規程データ配置は「外部送信回避」の方針と整合するか要確認。
5. **★ 試用URL（Cloudflare Tunnel）への実規程掲載の承諾**（7.5）。
   遠隔から試用いただくための一時公開URLを用意するが、通信は Cloudflare を
   経由する。LLM推論と規程データの保管は開発機内で完結する一方、
   質問文と回答中の条文テキストは外部事業者のネットワークを通過する。
   この点を明示したうえで、**実規程を載せてよいかの可否をいただく**。
   不可の場合はダミー規程での公開に切り替え、実規程は対面デモのみで扱う。
