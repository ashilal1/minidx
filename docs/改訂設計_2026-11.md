## 1. システムの概要

社内規程（Word）を取り込み、社員の質問に**登録した条文だけを根拠に**短く答えるシステム。
答えの根拠は、原本 PDF の該当箇所に色を付けて見せる。

**絶対条件**: 規程に書かれていない質問に、それらしい回答を一度も出さない（誤回答率 0%）。
答えられるのに断る「過剰棄却」は 20% まで許容する。迷ったら断る側に倒す。

このため、AI（LLM）に「答えてよいか」を判断させない。**答えてよいかはプログラムが機械的に判定する**。
AI の仕事は、プログラムが選んだ条文の範囲で短い日本語を書くことだけ。

**構成**: すべて社内の PC 1台で動く。外部の AI サービスやインターネットは使わない。

| 部品 | 使うもの |
|---|---|
| 文章を書く AI | Ollama 上の小型モデル（3B 級。最終的なモデルは評価で決める） |
| 意味の近さを測る AI | bge-m3（Ruri v3 と評価で比べる予定） |
| 語の一致で探す | BM25（形態素解析: fugashi） |
| 保存 | SQLite のファイル1つ |
| 画面 | Streamlit（社員用と管理者用） |

## 2. 処理の流れ

★ が今回の改訂で変わる・加わるところ。

### 2.1 取込（管理者が規程を登録する）

```
regulations/ フォルダ（Word と、同じ名前の PDF）
   │  ★ このフォルダの中身＝現行版。取込のたびに全件作り直す（旧版が残らない）
   │  ★ ファイル名から「規程名」と「改訂日」を分けて保存。同じ規程が2ファイルあればエラーで止める
   ▼
Word を読み、条単位に分割（長い条は項単位、表は1表1チャンクで各行を「列見出し: 値」に）
   │  ★ 検索用のテキストの先頭に「規程名・条番号（・章）」を自動で付ける（表示は本文のまま）
   ▼
bge-m3 でベクトル化 → SQLite に保存
   │
   ▼
同じ名前の PDF があれば、各条文が原本のどこにあるかを探して保存（画面で色を付けるため）
```

### 2.2 質問（社員が質問する）

```
質問文
   │  ★ 言い換え対応表で、規程側の語に置き換える（例: 泊まり → 宿泊）
   ▼
検索: 意味の近さ（bge-m3）＋語の一致（BM25）を合わせて上位5件
   ▼
ゲート1（AI を呼ぶ前の関所）
   │  ・質問の語が規程に1語も無い → 断る
   │  ・一番近い条文との近さが閾値未満 → 断る
   │  ここで断れば AI は一度も呼ばれない＝作り話は起こりえない
   ▼ 通過
AI が1行の回答を書く（引用できる条文番号は選択肢として固定。存在しない引用は出力できない）
   │  ★ 回答は1行に短く。小型モデル。起動時に事前読み込み。時間切れは断る
   │  ★ AI に渡すのは条全体（項だけが当たっても、原則と例外の両方を読ませる）
   ▼
ゲート2（AI の回答をプログラムで検証）
   │  ・AI が「答えられない」と言った → 断る（「答えられる」は信用しない）
   │  ★ 回答中の単位付きの数字（円・日・か月・年・回・時間・% など）が、引用した条文に無い → 断る
   │  ★ 表の場合、数字の直前の行ラベル（部長など）と同じ行にその数字が無い → 断る
   ▼ 通過
回答＋根拠（規程名・条番号・原本 PDF の色付け）を表示
   │  断った場合は固定の文言だけを出し、参考条文も出さない
   ▼
すべての質問を質問ログに記録（答えた／どの関所で断ったかを分けて）
   │  ★ 引用を「規程名・改訂日・条番号」の文字でも残す（再取込で番号が変わっても追える）
   ▼
管理画面: 未整備の質問一覧（多い順）・回答済み一覧・取込状況・CSV 出力
       ★ 設置 PC の上でだけ開ける別 URL（admin.py）
```

## 4. 論点ごとの「問いの意図」

改訂にあたって、次の問いを一つずつ仕様と照らして決めた。それぞれ**何を確かめたかったか**を残す。

| 論点 | 問い | 問いの意図 | 結論 |
|---|---|---|---|
| 1 | 数値照合を金額以外に広げるか | 10/5 で回答を「短く」と合意した結果、回答の中身は日数・期限になる。その中身が無検証なら、短くした分だけ危険が増える。照合の範囲と過剰棄却のどちらを取るかを決めたかった | 単位付きの数字すべて |
| 2 | 表の行の取り違えをどう防ぐか | 仕様の質問例そのものが表の質問。小型モデルに替えると取り違えが増えるので、モデルを替える前に安全網が要るかを決めたかった | 行ラベルと数字の組を照合 |
| 3 | 規程をまたぐ取り違え | 1本の今は見えない問題が、15本で必ず出る。先に手を打つか、出てから直すかを決めたかった | 条文側に規程名を付ける（社員は規程名を知らなくてよい） |
| 4 | 回答の形と速度 | 仕様の「わかりやすく回答」と、10/5 の「短く・原本で・普通の PC で速く」は引っ張り合う。どこで折り合うかを決めたかった。回答文を無くす案は仕様から外れることも確認したかった | 1行回答＋小型モデル＋事前読み込み |
| 5 | 旧版の除外 | 調べたら、今の取込では新しい版を入れると旧版が残る作りだった。版管理の画面（Phase 2）を作らずに旧版を確実に外す方法を決めたかった | フォルダ＝現行版、毎回全件作り直し |
| 基盤 | 実行環境・埋め込み・ベクトル DB は見直すか | 記事が様々な構成を勧めていたので、精度に効くものと効かないものを分けて確認したかった | 実行環境と DB は維持。埋め込みは評価で比べる（決定） |
| チャンク | 長い条をどこで切るか | 記事が警告する「原則と例外の分断」が、今の項分割で起きうるかを確認したかった | 検索は項、AI と画面は条全体（決定・実装済み） |
| 6〜9 | 対応表・管理画面・Excel・評価 | 10/5 の先方要望と合意を、仕様の範囲でどう実装するかを決めたかった | おすすめどおりに決定（対応表・管理画面の分離は実装済み、Excel は Word に変換） |

## 6. 記事との比較

対象: ユーザー指定の6記事のうち読めた5本（詳細は記事調査メモ）。

### 6.1 同じところ

| 項目 | 記事 | minidx |
|---|---|---|
| ローカルで完結させ、文書を外部に送らない | 全記事 | 同じ |
| 実行環境に Ollama | EQUES・コプラス・Qiita | 同じ |
| 埋め込みに BGE-M3 を候補にする | EQUES・コプラス | 採用中 |
| 意味検索だけでなくキーワード検索を併用 | EQUES・コプラス | BM25 を併用 |
| 文字数でなく条・見出しの切れ目で分割 | EQUES・コプラス・Qiita | 条単位 |
| 表を崩さず、人が確認できる形にする | EQUES・コプラス | Word から行ごとに構造化。Markdown の写しを人が確認できる |
| PDF と Word を二重に登録しない | コプラス | PDF は表示だけに使う |
| 根拠の文書名・条を示す | EQUES・コプラス | 規程名・条番号＋原本 PDF の色付け |
| 「検索」と「回答の忠実さ」を分けて評価し、変更のたびに同じ質問で測る | EQUES・コプラス | 評価スクリプトで同じ考え方（検索再現率と回答正確性を分けて出す） |

| 質問・検索結果・回答をログに残す | EQUES・コプラス | 全質問を記録 |

### 6.2 違うところ

| 項目 | 記事 | minidx | 理由 |
|---|---|---|---|
| **資料にない質問を止める方法** | プロンプトで「資料にないことは答えない」と指示するだけ。誤回答0%を実現する方法はどの記事にも無い。「ハルシネーションは完全には防げない」と明言する記事もある | **プログラムで2回止める**。AI を呼ぶ前の関所（ゲート1）と、回答の機械的検証（ゲート2） | 誤回答0%が絶対条件。AI の自己申告は信用しない |
| 引用の確かめ方 | 文書名を書かせる | 引用できる条文番号を選択肢として固定し、存在しない引用を出力できなくする。さらに数字を条文と照合 | 小型モデルは出典の書き方がぶれる（記事でも指摘） |
| ベクトル DB | Chroma・Qdrant・pgvector など | 使わない（numpy で全件比較） | 規模が小さく、精度にも効かない。客先 PC に置くものを減らす |
| フレームワーク | LangChain・LlamaIndex | 使わない | 規模に対して運用の負担にしかならない |
| 質問の書き換え | AI で subquery に分ける・書き換える（Qiita） | しない。代わりに管理者が直す言い換え対応表（提案中） | AI の書き換えは遅く、誤りが検索をずらす。対応表は決定的に動き、責任者も明確 |
