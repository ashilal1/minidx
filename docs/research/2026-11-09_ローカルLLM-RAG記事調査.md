## 1. 結論（先に）

1. **minidx の骨格は、記事が勧める構成とほぼ一致している。** ローカル完結、Ollama、bge-m3、キーワード検索との併用、条番号での分割、原本の確認、全質問のログ。方向は間違っていない。
2. **「誤回答0%」を実現する方法を示した記事は1本もない。** C は「ハルシネーションは完全には解決できない」、B は「RAG は間違えない仕組みではない」と書いている。どの記事も、対策はプロンプトでの指示（「資料にないことは答えない」）止まりで、**機械的な検証で棄却する仕組みは出てこない。** minidx の二段ゲートは、記事の水準より一歩進んだ部分であり、価値の中心である。
3. **一番の不足は「評価」。** A・B・D がそろって「検索が当たったか」と「回答が資料に忠実か」を分けて測り、同じ質問集を文書やモデルを変えるたびに使えと書いている。minidx は評価スクリプトが未実装で、0% をまだ一度も測っていない。
4. **ハードウェアの現実は厳しい。** F の目安では、メモリ 16GB の PC は「お試し」の区分（2B〜8B を4ビット量子化）にあたる。RAG の実務利用は「VRAM 12〜16GB＋RAM 32GB 以上」とされている。CPU だけの運用は「体験用途」と書かれている。客先の「16GB の普通の PC で10秒」は、**LLM に長い文章を書かせる設計のままでは届かない見込みが高い。** 11/8 の実測（M1 8GB で 7B はタイムアウト、3B は12〜14秒）とも合う。
5. したがって設計の軸は、**「検索＋機械検証を主役にし、LLM の役割を最小にする」** のが記事の知見とも客先の条件とも整合する。

## 2. 記事ごとの要点

### A. EQUES「ローカルLLMでRAG構築｜5ステップ」

- 5ステップ: ①対象文書を絞りテキスト化（最初は1部署の数十文書）②意味の切れ目でチャンク化し、メタデータ（文書名・部署・機密区分・版数）を付ける ③同じ埋め込みモデルで索引と質問をベクトル化 ④上位数件を LLM に渡し、根拠の文書名を示させる。型番・条番号のような質問にはキーワード検索を併用 ⑤実際の質問と正解文書で質問集を作り、「検索上位に入ったか」と「回答の忠実性」を分けて記録する
- 前処理: 表や段組みが崩れたまま取り込むと後で取り戻せない。変換後のテキストを人が開いて、表の行と列の対応を確認する
- **分割の失敗例**: 文字数で機械的に切ると、条文の原則と例外が別のチャンクに分かれ、例外だけ拾われて逆の回答になる
- **埋め込みの入力上限**: multilingual-e5-large は512トークンを超えた分を捨てるため、長い条文の後半が「規程にあるのに出てこない」形で現れる
- 埋め込みの候補: multilingual-e5-large、BGE-M3、**Ruri v3**（名古屋大学の日本語特化。8,192トークン）。自社の文書と想定質問で比べて選ぶ
- 実行環境: 1台で試すなら Ollama か llama.cpp、複数人なら vLLM
- セキュリティ: 閲覧権限は**検索段階**で絞る（LLM への「見せるな」の指示は破られうる）。文書に紛れた命令によるプロンプトインジェクション対策。質問・検索文書・回答のログを残し、保存期間と閲覧者を決める。廃止版はすぐ索引から外す。モデル更新時は質問集で測り直してから切り替える
- 誤回答率や回答拒否の仕様には触れていない

### B. コプラス「ローカルLLM RAGの作り方」（最も新しく、運用の記述が厚い）

- 主張: 精度は LLM の賢さより、**文書の整え方**（重複・旧版の排除、表の崩れ防止、チャンクの切り方）と検索の当たり方で決まる
- 社内規程は章・条・項のまとまりを崩しすぎない。表（給与テーブル、休暇の対象者一覧など）は PDF 抽出で列が混ざるので、人が読める Markdown の表に直してから入れる
- PDF と Word を両方入れると重複になる。テスト時はどちらか一方
- 小型モデルは出典の書き方が安定せず、文書名の取り違えや根拠の言い換えすぎが起きる。対策は回答を短くし、参照元の書き方を制約すること
- 誤回答の切り分け: 回答ではなく**検索で拾われたチャンク**を見て、「文書が悪いのか、検索が外れたのか、LLM が補ったのか」を分ける
- 評価: 約10問のテスト質問。正解の条番号を人が先に確認しておく。「資料に書かれていない福利厚生」で止まれるかも確認する。テスト質問の例は、有給の取得条件、休職、復職手続き、服務規律、ハラスメントの相談先、賃金の支払いルール、安全衛生、退職手続き、資料にない福利厚生、管理職限定資料が混ざった場合
- 運用チェックリスト: 月次で旧版・重複を確認し、ログから頻出質問と誤回答の傾向を見る。改定時は旧版を検索対象から外す。モデル入れ替え時は同じテスト質問で比べる。担当を1人に寄せない。誤回答の報告窓口を置く
- 権限: 部署ごとに DB を分けるか、文書ごとに閲覧属性を持たせて検索時に絞る。人事評価や給与の資料を1つの DB に入れない
- モデルの記述（記事の時点）: gpt-oss-20b（16GB で動く設計、DL 14GB）、qwen3.5 9b（6.6GB）、gemma4 26b（約16〜19GB）。埋め込みは bge-m3（567M、1.2GB、8K）、embeddinggemma（300M、622MB、2K）
- 実行時はコンテキスト分のメモリが追加で要る。RAG では埋め込みモデルも同時に動くので、ダウンロードサイズだけで PC を決めない
- 既製ツール: LM Studio（16GB 以上推奨、Windows は AVX2 必須）、AnythingLLM（MIT。複数ユーザーと権限は Docker 版のみ）
- 精度の数値は一切なし

### C. Qiita「RAGの秘密を解き明かす(1)」（2024年の概念解説）

- RAG とファインチューニングの比較、RAG の基本フローの説明が中心。コード・数値・プロンプトは無い
- 筆者の立場: ハルシネーションは完全には解決できず、リスク管理で影響を小さくする
- 設計の材料としては薄い。登場するモデル名も古い

### D. Qiita「ゼロからはじめるRAG：完全ローカル構築ガイド」（2024年）

- 構成: Streamlit＋Ollama＋PostgreSQL/pgvector。LLM で質問を subquery に分割・書き換え → 各 subquery で多めに取得（上位10件）→ **リランクして上位3件** → 会話履歴とともに LLM へ
- リランクの効果例（1件、定性的）: リランクなしでは「2024年度の売上」に来年度のデータを拾ったが、リランクありでは正しく2024年度を拾った
- チャンク分割の例: 文字数（100字、重なり0/20）、トークン数（500、重なり50）、見出し階層を親情報としてチャンクに付ける方法
- ロール（employee / manager）による参照制限
- 埋め込みモデルを替えたら全件再埋め込みが必要
- 実行環境・速度・評価の数値は無い。リランクの方式の記述に食い違いがある

### F. EQUES「ローカルLLMとは？必要なPCスペック2026」

- 決め手は CPU ではなく **VRAM（Mac はユニファイドメモリ）**。必要量の目安は「パラメータ数×1パラメータのバイト数」。7B なら16ビットで約14GB、4ビットで約3.5GB、これに作業領域の数GBが加わる
- 用途別の目安:

| 区分 | VRAM | RAM | モデルの目安 |
|---|---|---|---|
| お試し（チャット・要約） | 8GB | 16GB 以上 | 2B〜8B の4ビット量子化（Gemma 4 E2B/4B、Llama 3.2 3B など） |
| 実務利用（RAG・文書作成） | 12〜16GB | 32GB 以上 | 8B〜20B |
| 本格運用（30B・複数人） | 24〜32GB | 64GB 以上 | 27B〜31B |

- CPU だけでも小型モデル（2B〜4B）は動くが遅く、体験用途と割り切るのが現実的
- Mac は1人で使う範囲なら実用的だが、同クラスの NVIDIA GPU より遅い
- 企業利用では、同時利用、アクセス管理、監査ログ、モデル更新の体制が必要
- ハルシネーション対策の記述は無い

## 3. minidx との突き合わせ

### 3.1 すでに記事の水準を満たしている（または超えている）点

| 記事の推奨 | minidx の現状 |
|---|---|
| 文書を外部に出さない（A, B, F） | Ollama でローカル完結。外部 API 禁止（AGENTS.md §2） |
| 条番号・見出しで分割し、文字数で機械的に切らない（A, B, D） | 条単位で分割し、長い条だけ項単位に再分割（`split.max_chars`） |
| キーワード検索の併用（A, B） | BM25＋bge-m3、RRF で融合 |
| 表を崩さない。人が確認する（A, B） | 取込の正本は Word（PDF からは取り込まない）。Markdown の写しを人が確認できる |
| PDF と Word の二重登録を避ける（B） | PDF は原本表示だけに使い、検索対象には入れない |
| 根拠を示す（A, B） | 規程名・条番号のカードと、原本 PDF の該当箇所の色付け |
| 資料にない質問で止まる（B） | **プロンプトでなく機械的に止める**: ゲート1（類似度・語彙）で LLM を呼ぶ前に棄却、ゲート2（引用の集合照合・金額の実在確認）で生成後に棄却 |
| 拾われたチャンクで誤回答を切り分ける（B） | query_log に検索ヒットと判定の内訳を記録 |
| 埋め込みの入力上限に注意（A） | bge-m3 は 8K トークン（B の記述）。条文長では問題になりにくい |

### 3.2 足りない点（優先度順）

| # | 不足 | 根拠 | 影響 |
|---|---|---|---|
| 1 | **評価セットと評価スクリプトが無い** | A, B, D がそろって最重要視。検索と忠実性を分けて測り、変更のたびに同じ質問で測る | 0% が未計測。モデルを 3B 等に替える判断もできない |
| 2 | **客先の PC で動く速さになっていない** | F: 16GB は「お試し」区分、CPU だけは体験用途。B: 埋め込みとコンテキスト分のメモリも要る | 「16GB で10秒」に届かない。11/8 実測で 7B は 8GB 機でタイムアウト |
| 3 | **規程が1本しかない** | A, B: 文書の整備が精度を決める | 15本になると語彙と類似度の分布が変わり、`tau_cos` 等の再校正が必要 |
| 4 | **版の管理（旧版を外す）の運用が無い** | A, B: 旧版が残る失敗は半年後の改定時に起きやすい | 改定のたびに旧版の条文で答えるおそれ。誤回答0%に直結 |
| 5 | **言い換えの吸収** | 客先要望（10/5）。B は利用者に語を足させる、D は LLM で質問を書き換え | 「泊まり＝宿泊」のような過剰棄却が残る |
| 6 | **リランクが無い** | A（明示なし）、D（上位10件→3件で改善例） | 検索の取り違えが残る。ただし追加のモデルでメモリと時間を食う |
| 7 | **管理画面とログの閲覧制御** | A, B: ログの閲覧者を決める。F: アクセス管理 | 10/5 の合意は「別 URL」。LAN 内の誰でも URL を知れば聞きづらい質問のログを読める |
| 8 | 埋め込み・LLM の比較検証をしていない | A: 自社文書で比べて選ぶ（Ruri v3 など）。B, F: 新しい小型モデルの候補 | qwen2.5 は記事の時点で旧世代。より小さく速い候補がある可能性 |

### 3.3 記事の推奨のうち、minidx では採らない（または慎重にする）べきもの

| 記事の推奨 | 採らない理由 |
|---|---|
| LangChain / LlamaIndex / Chroma 等の採用（A, B, D） | 数百〜2,000条文の規模では運用の負債になる。AGENTS.md §2 で禁止済み |
| LLM による質問の書き換え・subquery 分割（D） | 生成が1回増えて遅くなる。書き換えの誤りが検索をずらし、ゲート1の判定対象もずれる。言い換えは**管理者が直せる対応表**（決定的に動く）で吸収する方が 0% の方針と合う |
| 会話履歴を LLM に渡す（D） | 10/2 に「1問ずつ」の画面に決めた。前の質問の文脈が誤解を生むため |
| プロンプトの指示だけで回答を制御する（A, B） | LLM の自己申告を最終判定に使わない（AGENTS.md §5）。機械照合を残す |
| 誤回答の報告窓口・フィードバック（B） | フィードバック収集は Phase 2（AGENTS.md §9）。必要なら客先と範囲を合意してから |

## 4. 設計の方向（たたき台。一緒に詰める）

### 4.1 LLM の役割を最小にする

記事の知見（16GB・CPU では小型モデルしか現実的でない。小型モデルは出典がぶれる）と、10/5 の合意（根拠は原本、回答は短く）から、次の3段階が考えられる。

| 案 | 中身 | 速さ | 安全性 | わかりやすさ |
|---|---|---|---|---|
| 1. 回答文なし | 検索とゲート1で条文を特定し、原本の該当箇所を見せるだけ | ◎（11/8 時点で、ゲート1止まりの質問は0〜3秒） | ◎ 生成が無いので幻覚が起きない | △ 社員が条文を読む |
| 2. 1行回答（推奨候補） | 小型モデルに「上限◯円」程度の1行だけ書かせ、ゲート2で検証。主役は原本 | ○ 3B で12〜14秒（M1 実測、要 Windows 実測） | ○ 書く量が少ないほど照合が確実 | ○ |
| 3. 現状の回答文 | 7B で文章を生成 | × 8GB 機でタイムアウト | ○ | ◎ |

「案2を基本にして、時間内に答えが出なければ案1に落とす」という組み合わせもできる。

### 4.2 優先順位（案）

1. **評価スクリプトと評価セット**（回答可能15・回答不能15）。B のテスト質問の観点（資料にない福利厚生、管理職限定資料など）も取り入れる
2. 客先に近い PC（Windows、16GB、GPU なし）での速度の実測。3B 級と、記事に出る新しい小型モデル（Gemma 4 E2B/4B 等。Ollama での提供有無とライセンスは要確認）を比べる
3. 残り14本の受領と取込（Excel は Word に変換。10/5 合意）。そのうえで閾値を再校正する
4. 言い換え対応表（管理者が編集。検索語の展開にだけ使い、ゲート2は変えない）
5. 版の管理: 規程1本につき現行版は1つだけを検索対象にする取込ルール
6. リランクは、評価で検索の取り違えが目立ったら検討する（メモリと時間の予算と相談）

### 4.3 客先に確認したいこと（記事から出てきた論点）

- 管理職だけが見てよい規程はあるか（A, B: 権限は検索段階で絞る必要がある。あれば DB を分けるか属性で絞る）
- 質問ログを見てよいのは誰か。保存期間はどうするか（A。聞きづらい質問が残る、という 10/5 の話とも関わる）
- 規程が改定されたとき、誰がいつ再取込するか（B の運用チェックリスト）
- 設置する PC の仕様（メモリ、GPU の有無、CPU の世代。LM Studio は AVX2 必須とあり、Ollama 系も CPU 世代の影響を受けうる）
